01 · Git in GitHub

Git spremlja lokalne spremembe. GitHub jih poveže z ekipo.

Git

Program za nadzor različic. Na računalniku hrani zgodovino projekta; lahko dela tudi brez interneta.

GitHub

Spletna storitev, kjer gostimo oddaljeni Git repo, pregledujemo spremembe in sodelujemo.

Repozitorij

Projektne datoteke in zgodovina njihovih sprememb. Lokalni repo je tvoja kopija; GitHub repo je skupna kopija.

Commit

Lokalno shranjena, poimenovana točka zgodovine. Sporočilo pove namen spremembe.

Git in GitHub nista ista stvar. Najprej shraniš commit lokalno; s push ga pošlješ na GitHub, da ga ekipa vidi.

01 · miselni model

Od urejanja do skupne zgodovine.

urejanje→staging→commit→push→GitHub

Working directory

Delovno okolje z datotekami, ki jih urejaš. Spremembe tu še niso shranjene kot commit.

Staging

Izbor datotek ali vrstic (sprememb), ki jih želiš vključiti v naslednji commit. Preglej ga.

Lokalni commit

Točka zgodovine na tvojem računalniku; še ni nujno objavljena na GitHubu. Vedno dodaj vsaj kratek komentar z opisom spremembe za preglednost.

Oddaljeni repo

Skupna kopija na GitHubu. push pošlje; pull prenese in vključi spremembe.

02 · nastavitev pred skupnim delom

Git potrebuje ime avtorja in e-pošto.

git config --global user.name "Ime ali vzdevek"
git config --global user.email "tvoj-email@example.com"
git config --global --list

Git identiteta

Ime in e-pošta se zapišeta v metapodatke tvojih commitov. Uporabi ime/vzdevek in e-pošto, ki jo želiš povezati z GitHubom.

Preveri nastavitev

Prvi dve nastavitvi veljata za vse lokalne repozitorije. --global --list pokaže shranjene nastavitve.

To ni prijava v GitHub. Za prijavo v VS Code uporabi Accounts → Sign in with GitHub in potrdi prijavo v brskalniku. GitHub gesla ne vpisuj v Git ukaze; za GitHub se prijavi prek brskalnika/credential managerja, ne prek account password prompta.

02 · kloniraj in sinhroniziraj

clone naredi kopijo. pull jo osveži.

git clone <https://github.com/MatijaPI/git-github-delavnica.git>
cd git-github-delavnica
git status
git pull --ff-only origin main
1
git clone

Enkrat prenese repo in nastavi povezavo do oddaljenega repozitorija.

2
git status

Potrdi, da si na pričakovani veji in da nimaš nepričakovanih sprememb.

3
git pull --ff-only origin main

Osveži lokalni main, kadar ni lokalnih odstopajočih commitov; ob zapletu se ustavi in opozori.

Pulla ne izvajaj na slepo: najprej poglej git status in preveri trenutno vejo. Pred začetkom naloge uskladi main.

03 · ekipni potek

main je skupna osnova. Vsak posamezen task živi v svoji veji.

main       ──●───────────────●─────────────●──→
              \              ↑ PR + pregled
feature/ime   └──●────●──────┘
1
Osveži osnovo

Na main prenesi zadnje spremembe.

2
Ustvari vejo za nalogo

Spremembe pripravljaj ločeno, ne neposredno na main.

3
Commitaj in push-aj vejo

Majhni commiti in pregledan diff olajšajo sodelovanje.

4
Odpri PR v main

Ekipa pregleda spremembe in jih po dogovoru združi.

03 · poimenovanje vej

Ime veje naj pove vrsto dela in namen.

feature/<podsistem>-<kratka-naloga>
fix/<podsistem>-<kratka-naloga>
docs/<tema>-<kratka-naloga>
test/<podsistem>-<kratka-naloga>
git switch -c feature/demo
Prej: 
git checkout -b feature/demo

Primeri

feature/drive-encoder-check
fix/imu-axis-sign
docs/power-pinout
test/arm-limit-switch

Skupna pravila

Mala angleška tiskana črka, številke ali vezaji; brez presledkov in imen oseb. Ena veja naj predstavlja eno nalogo.

Dogovor: tip/podsistem-kratek-opis. Če uporabljamo številke nalog, jih dodamo za tip: feature/42-drive-encoder-check. Ne mešajmo formatov po občutku.

03 · ukazi, ki jih potrebujemo

Najprej preveri spremembe. Nato izberi, shrani in deli.

git status

Pokaže trenutno vejo ter spremenjene, pripravljene in nespremljane datoteke. Uporabi ga, ko nisi prepričan, kaj se dogaja ali želiš videti stanje svojega working directoryja.

git diff

Prikaže vrstice, spremenjene v že spremljanih datotekah, ki še niso v stagingu.

git add pot/do/datoteke

Izbrane spremembe pripravi in vključi v naslednji commit. Ni še objava na GitHubu.

git diff --staged

Prikaže točno to, kar bo šlo v commit. Posebej uporabno za nove datoteke.

git commit -m "Sporočilo"

Iz staginga naredi lokalni commit. Sporočilo naj opiše spremembe.

git push / git pull

Push pošlje commite na oddaljeni repo; pull prenese in vključi oddaljene spremembe v trenutno vejo.

Ritem, ki si ga velja zapomniti: status → diff → add → diff --staged → commit → push.

03 · pripravi in shrani

Commit vsebuje samo to, kar si izbral.

git status
git diff
git add test.md
git diff --staged
git commit -m "Added test.md file"

Preglej git diff

Ali sprememba ustreza namenu? Nova, še nespremljana datoteka tu še ni prikazana.

Izberi z git add

Dodaj samo spremenjene in relevantne datoteke. Izogni se git add ., če nisi pregledal vsega.

Preglej staging

git diff --staged pokaže tudi vsebino nove datoteke, pripravljeno za commit.

Napiši uporaben commit

Uporabi glagol in predmet: »Changed/added/removed [feature]«, ne samo »fix«.

03 · deli spremembo

push objavi tvoje commite za ekipo.

# Prva objava nove veje:
git push -u origin feature/demo

# Nadaljnji commiti na isti veji:
git push

origin

Običajno ime za oddaljeni repo, iz katerega si kloniral.

-u

Prvič poveže lokalno vejo z vejo na GitHubu; pozneje lahko uporabiš krajši git push.

Commit je lokalen, dokler ne push-aš. Push objavi vejo, ne združi je v main.

03 · pull request in merge

PR je zahteva za pregled sprememb in združitev z vejo.

01

Pull request

Na GitHubu predlagaš, da se tvoja veja združi v main. Opišeš kaj, zakaj in kako si preveril.

02

Pregled

Kolega pogleda diff, postavi vprašanja ali predlaga izboljšave. Popravki na isti veji se pokažejo v istem PR-u.

03

Merge

Po dogovorjenem pregledu pooblaščeni član (predlagam vodje ekip) združi vejo v ciljno vejo, običajno main.

Po mergeu

Vsi osvežijo lokalni main z git pull, preden začnejo naslednjo nalogo.

Merge ni samodejni dokaz pravilnosti. Spremembe roverja še vedno zahtevajo ustrezne teste, tehnični pregled in varne postopke.

04 · ustvarjanje pull requesta

Kako odpreti PR na GitHubu.

1
Odpri zavihek Pull requests

Klikni New pull request; po pushu se lahko pokaže tudi Compare & pull request.

2
Izberi veji

base je cilj, običajno main; compare je tvoja delovna veja.

3
Opiši in preglej diff

Dodaj jasen naslov in kratek opis ter preveri, da so prikazane samo tvoje spremembe.

4
Klikni Create pull request

PR je odprt za pregled, vendar še ni združen v main.

Popravke committaj in pushaj na isto vejo; odprti PR se samodejno posodobi.

04 · nagradni izziv

Izziv poišči v datoteki repozitorija.

V korenski mapi odpri zdaj vidno datoteko izziv.md. Rešitev vpiši neposredno v polje Odgovor v tej datoteki.

branch→rešitev→commit→push→PR
1
Ustvari svojo vejo

Uporabi izziv/marsovec-vzdevek in unikaten vzdevek.

2
Zapiši rešitev

V svoji veji dopolni samo polje Odgovor v izziv.md.

3
Commitaj in objavi

Uporabi ukaze iz README.md na GitHubu, nato ustvari PR v main.

Ne spreminjaj datotek drugih udeležencev ali skupne veje main. Zmaga prvi pravilno rešen PR po času odprtja. Ker vsi spreminjajo isto vrstico, združimo samo zmagovalni PR; ostale pregledamo in zapremo brez mergea.

04 · zaključek izziva

Rezultati.

veja→push→pull request→pregled→merge
1
Odpremo PR

Izberemo vejo udeleženca kot source in main kot target; vidimo spremembo.

2
Pregled spremembe

Skupaj si oglejmo diff in kje se podajajo komentarji.

3
Merge in osveži

Združimo PR; posodobite lokalni main.

Vsak udeleženec odpre PR v main; skupaj pregledamo pravilnost rešitve.

05 · datoteka .gitignore

Git naj spremlja projekt, ne lokalnega nereda ali skrivnosti.

Datoteka .gitignore pove Gitu, katere še nespremljane datoteke naj privzeto prezre. Pravila veljajo za celoten repozitorij ali izbrane mape.

# Tipični primeri
.env  ,  *.log  ,  __pycache__/. ,  .venv/. ,  .DS_Store. ,  build/. ,  dist/

Ponavadi ignoriramo

Lokalne nastavitve in skrivnosti, loge, začasne datoteke, cache, virtualna okolja in generirane build izhode.

Ne skrivaj projektnih virov

Ne ignoriraj izvorne kode, dokumentacije, pomembnih konfiguracij ali datotek, potrebnih za ponovitev projekta.

.gitignore ne odstrani že spremljanih datotek in ni zaščita za skrivnost, ki je že commitana. Če skrivnost po nesreči objaviš, jo takoj prekliči in obvesti ekipo.

Povzetek

Git nam omogoča sledenje lokalni zgodovini datotek, GitHub pa olajša sodelovanje v ekipi in pregled posameznih sprememb.
